# 用一个例子学会 FastAPI 的 async、线程池和并行计算

这篇文档只讲一件事：用户调用一个接口后，服务要做三步工作。

```text
1. CPU 计算一个很大的数值
2. 把结果写入文件 A
3. 把相同结果写入文件 B
```

例如，用户点击“生成报告”，服务要计算一组复杂规则的结果，然后分别生成给客户看的文件 A 和内部归档用的文件 B。

下面所有概念都围绕这一个例子解释。

## 先给结论

这三步不能用同一种并发方式处理：

| 工作 | 本质 | 合适的方式 |
|---|---|---|
| 计算数值 | CPU 一直在算 | 使用**进程**做真正的并行计算 |
| 写文件 A | 大多数时间在等磁盘 | 使用**线程**或异步文件库 |
| 写文件 B | 大多数时间在等磁盘 | 使用**线程**或异步文件库 |

最重要的一句话是：

> `async` 擅长处理“等待”；进程擅长处理“计算”。

不要因为看到了 `async`，就以为它能加快 CPU 计算。

---

## 先把四个词说成人话

### 1. CPU 计算：厨师真的在炒菜

假设 CPU 要算 1 亿次规则：每一步都要比较、相加、判断。这个过程中，CPU 一直有活干，就像厨师一直在切菜、翻炒。

```text
CPU：算、算、算、算、算……
```

这叫 **CPU 密集任务**。它的瓶颈是 CPU 的计算能力。

### 2. 写文件：厨师把菜交给传菜员后等待

写文件时，程序把内容交给磁盘，磁盘需要时间完成写入。多数时候 CPU 不需要持续计算，只是在等待磁盘通知“写完了”。

```text
程序：请把结果写入 A
磁盘：收到，正在写……
程序：等待写完
```

这叫 **I/O 密集任务**。网络请求、数据库查询、读取文件、写入文件，大多属于这一类。

### 3. 线程池：多个传菜员

线程池就是一组可重复使用的工作线程，可以把它理解为多个传菜员。

当主程序要写文件 A 时，它可以交给传菜员 1；要写文件 B 时，交给传菜员 2。两名传菜员分别等待自己的磁盘写入，主程序不必亲自站在原地等待。

```text
主程序：把“写 A”交给线程 1
主程序：把“写 B”交给线程 2
线程 1：等待磁盘写 A
线程 2：等待磁盘写 B
```

线程池适合**阻塞的 I/O 工作**。它不会让磁盘速度翻倍，也不会让纯 Python 的计算自动使用多个 CPU 核；它的作用是让等待中的工作不要堵住主程序。

### 4. async：主调度员不在等待时发呆

`async` 可以理解为主调度员的工作方式。

调度员收到“写文件 A”的任务后，如果这件事还在等磁盘，就先去处理别的事情；等磁盘说“写好了”，再回来继续。

```text
调度员：A 还没写完，先处理其他请求
调度员：B 还没写完，先维持 SSE 连接
调度员：A 写完了，回来收尾
```

`await` 的意思就是：**“我现在得等；请先运行其他可以继续的任务。”**

它不是新线程，也不是新 CPU 核。

## 什么是 ASGI，和 FastAPI 有什么关系

ASGI 是 FastAPI 与 Uvicorn 之间使用的一套通信规范。可以把它理解成“餐厅前台和后厨的固定沟通方式”。

- **Uvicorn**：接收浏览器请求的前台；
- **FastAPI**：决定请求应该调用哪个函数的后厨；
- **ASGI**：两者之间的工作约定；
- **事件循环**：`async` 任务的调度员。

简化后的调用链如下：

```text
浏览器发请求
    ↓
Uvicorn 接收请求
    ↓
FastAPI 找到对应路由
    ├─ async def：交给事件循环调度
    └─ def：交给线程池中的线程执行
```

ASGI 的价值是：一个 FastAPI 服务可以在等待网络、等待文件、等待队列消息的同时，继续处理其他请求。PMS 的 SSE 长连接正是这种场景，见 [PUMA_Server/api/sse_stream.py](../PUMA_Server/api/sse_stream.py)。

## 同一个需求，三种错误或正确的设计

现在回到“计算数值，再写 A 和 B”。假设计算需要 10 秒，每个文件写入需要 2 秒。

### 设计一：全部顺序执行

```text
计算 10 秒 → 写 A 2 秒 → 写 B 2 秒 → 返回
```

总时间约为：

$$10 + 2 + 2 = 14\text{ 秒}$$

这是最容易写的方式，但等待写 A 时什么也没有做，写 B 也必须继续等。

### 设计二：把所有事情都放进 `async def`

很多人会误以为这样就“异步”了：

```text
async def generate():
    做 CPU 计算
    普通方式写 A
    普通方式写 B
```

这是**错误理解**。

如果“做 CPU 计算”和“普通方式写文件”都是同步函数，那么它们会一直占住 FastAPI 的事件循环。虽然函数名字前面有 `async`，但服务在这段时间仍然不能顺畅调度其他异步请求。

所以：

> `async def` 不是加速按钮。里面没有可等待的异步操作时，它只是一个会阻塞的异步函数。

### 设计三：正确拆分工作类型

正确的思路是先看每一段工作的性质：

```text
第一步：CPU 计算
    → 交给独立进程
    → 让另一个 CPU 核真正参与计算

第二步、第三步：写文件 A 和 B
    → 计算完成后，同时交给两个线程
    → 两个线程分别等待磁盘写入
```

时间线大致如下：

```text
第 0～10 秒：进程 1 计算数值
第 10～12 秒：线程 1 写 A，同时线程 2 写 B
第 12 秒：两个文件都完成，接口返回
```

总时间约为：

$$10 + \max(2, 2) = 12\text{ 秒}$$

这里的“同时”有两层意思：

- 计算放进**另一个进程**，可获得真正的多核并行能力；
- 两个写文件任务放进**两个线程**，可以同时等待两个独立的磁盘 I/O 操作。

如果 A 和 B 写到同一个文件、同一张 Excel 工作簿，或者必须严格按顺序写，就不能并发写。并发的前提是：两个任务互不修改同一份共享数据。

## FastAPI 中这套设计如何落地

对于很短的任务，可以在一个请求中等待结果：

```text
请求进入 FastAPI
    ↓
把 CPU 计算提交给进程池，并等待计算结果
    ↓
把“写 A”“写 B”提交给线程池，同时等待二者完成
    ↓
返回下载地址或结果
```

代码层面通常是以下组合：

- `asyncio`：让 FastAPI 路由等待任务时不堵住事件循环；
- `ProcessPoolExecutor`：执行 CPU 密集计算；
- `asyncio.to_thread()` 或 `run_in_threadpool()`：执行同步的写文件函数；
- `asyncio.gather()`：同时等待“写 A”和“写 B”。

不需要记住所有 API。先记住职责分工：

```text
asyncio：负责等待和调度
进程池：负责真正的 CPU 计算
线程池：负责传统阻塞 I/O
```

下面是伪代码，只看流程即可：

```text
async def generate_report():
    number = 等待进程池算出 number

    同时等待：
        线程池写文件 A(number)
        线程池写文件 B(number)

    返回结果
```

注意，CPU 计算函数应当是独立、只接收普通参数并返回普通结果的函数。这样它才能安全地交给进程池；不要把数据库连接、打开的文件对象或 Excel COM 对象直接传给子进程。

如果计算需要几十秒甚至几分钟，不应让浏览器一直等待 HTTP 响应。更合适的做法是：接口立即返回任务 ID，后台 worker 完成计算和写文件，前端再查询状态或通过 SSE 接收完成通知。

## 为什么 Python 的 CPU 计算需要进程

CPython 有 GIL（全局解释器锁）。简单理解：在一个 Python 进程中，多个线程一般不能同时执行 Python 的计算代码。

因此，下列做法通常不能让纯 Python 的计算变快：

```text
线程 1：计算前半部分
线程 2：计算后半部分
```

两个线程会轮流使用 Python 的执行权，而不是稳定地各占一个 CPU 核。线程仍然很适合写文件、网络请求等 I/O；但要让两段纯 Python 计算真正用上多个 CPU 核，应使用多个**进程**。

```text
进程 1：在 CPU 核 1 上计算前半部分
进程 2：在 CPU 核 2 上计算后半部分
```

多个进程不共享内存，交换数据需要额外开销。因此，小计算不要随便拆进程；只有计算时间明显大于进程通信成本时，进程池才值得使用。

## 和 PMS 代码的对应关系

PMS 已经有几种典型场景：

- [PUMA_Server/services/datamerge.py](../PUMA_Server/services/datamerge.py) 中的 `fetch_single_project_details()` 使用 `httpx.AsyncClient` 与 `asyncio.gather()` 并发等待 PMS HTTP 请求。这是“等待网络”的正确 async 用法。
- [PUMA_Server/api/sse_stream.py](../PUMA_Server/api/sse_stream.py) 中的 SSE 路由使用 `await queue.get()` 等待消息。这是“等待队列”的正确 async 用法。
- [PUMA_Server/api/report.py](../PUMA_Server/api/report.py) 中的 Sensor Map 路由会调用同步 Excel COM 操作；对应实现在 [PUMA_Server/services/sensormap/service.py](../PUMA_Server/services/sensormap/service.py)。这类工作不应直接占住事件循环，且 Excel COM 需要锁保护。
- [PUMA_Server/services/sensormap/service.py](../PUMA_Server/services/sensormap/service.py) 中的 `_EXCEL_COM_LOCK` 表示：即使使用线程，也不能让多个任务随意同时操作 Excel。它们必须排队。

这正好说明：选择 async、线程还是进程，不能只看函数是否耗时，而要看它**究竟在计算、等待，还是访问共享的外部程序**。

## 最后用一张表判断

| 你遇到的工作 | 问自己什么 | 通常选择 |
|---|---|---|
| 调用外部 HTTP 接口 | 大多数时间是在等网络吗？ | `async def` + 异步 HTTP 客户端 |
| 等待 SSE 消息或队列 | 大多数时间是在等消息吗？ | `async def` + `await` |
| 写两个互不影响的普通文件 | 可以同时等待两个磁盘写入吗？ | 线程池或异步文件库 + 并发等待 |
| 大量 Python 数值计算 | CPU 会持续计算很久吗？ | 进程池或后台计算 worker |
| 操作 Excel / Word COM | 外部程序是否线程安全？ | 串行访问，使用锁；不要盲目并发 |
| 任务很久 | 浏览器该一直等吗？ | 后台任务 + 状态查询或 SSE |

学习 FastAPI 并发时，不必先背 `asyncio` 的 API。每次只问一个问题：

> 这段代码是在让 CPU 计算，还是在等待外部结果？

CPU 在计算，就考虑进程；代码在等待，就考虑 `async`；传统阻塞 I/O 又不能改造时，就用线程池。
